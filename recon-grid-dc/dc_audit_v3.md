## S1 ['clean', 'has-blocking-issues']
### IMPORTANT: Zero-cut-point internal cut-face component produces a 0/0 NaN feature point. §5.5 L340-341 sets voxelFPCountBuf[voxelId]=compCount (enumerating ALL connectivity components as active slots) and computes each component FP as cutFPAccumBuf.sum/count with no count==0 guard; featurePointBuf (§3.4 L153) carries no valid flag (only voxelExternalFPBuf L151 has 'uint valid'). The v3 ablation cut-point-ownership fix (§5.3 L326 / §5.5 L343) binds a half-ablated edge's cut point ONLY to the surviving endpoint, so the deleted endpoint's vertToComp component receives count=0 while still occupying an enumerated slot — NaN = 0/0 is written into featurePointBuf[8*voxelId + comp_of_deleted_vertex].
FIX: In §5.5 add an explicit count==0 sentinel for cut-FP centroids and propagate a validity signal to §5.6. Concretely: (1) Give featurePointBuf a validity channel mirroring voxelExternalFPBuf — either add 'uint valid' (float3 + uint valid) to featurePointBuf in §3.4 L153, or define a NaN-free default sentinel. (2) State the centroid kernel as: 'for slot in 0..compCount-1: if cutFPAccumBuf[8*voxelId+slot].count > 0: featurePointBuf[...] = sum/count, valid=1; else valid=0 (skip, no write/NaN)'. (3) Make §5.6's partial-quad predicate 'holds that component cut-face FP' (L348) read this valid flag explicitly, so the 4/3/<3 rule excludes empty-component slots — define 'holds an FP' = valid==1. (4) Optionally tighten voxelFPCountBuf semantics so it enumerates only count>0 slots, but keeping dense compCount + per-slot valid is simpler given the static 8-slot/voxelId addressing. (5) Add the S1-I14 EditMode oracle already promised in §4.7/§5.11: a single ablated particle adjacent to alive neighbors yields a closed cut surface on the alive side with NO NaN FP and no NaN-cornered triangle on the deleted side. This is paper-aligned (newpaper_clean.txt L344: a component FP is the centroid of its cut points; zero cut points => no FP).

### minor: Empty-broadphase (K=0 candidate triangles) freezes the proxy instead of chasing the physical tool. §6.3 dispatches the finger-proxy as Dispatch(1,1,1) with a group of K=candidateTriCounter threads. The not-colliding 'chase physical tool' decision (P_t += clamp_step(P_A - P_t); done=2) lives INSIDE the per-iteration tid==0 reduction block (L415-416), which only executes if at least one thread runs. When the capsule-AABB broadphase returns zero candidates (tool fully clear of all tissue, candidateTriCounter==0), the group is empty, the kernel body never runs, and P_B/q_B are never written. The proxy stays frozen at its last position rather than converging to P_A, so ΔP=P_B-P_A stays nonzero and ComputeForceTorque (Eq27 F=K_p·ΔP) emits a phantom restoring force in exactly the case there is no contact at all - the same phantom-force class S3-IMP6 was meant to eliminate, but for the zero-candidate boundary rather than the near-but-not-penetrating one.
FIX: Guarantee the chase-physical-tool path runs even when candidateTriCounter==0: either (a) on the CPU side clamp the launched thread count to max(1, K) and have the lone thread treat K==0 as the sentinel/no-candidate case (v_ms sentinel -> P_t += clamp_step(P_A - P_t); q_B:=q_A; write back), or (b) in ReconGridManager, when candidateTriCounter==0 skip ProxyRelax and instead run a tiny ProxyChase kernel that sets P_B += clamp_step(P_A - P_B) and q_B:=q_A. State the K==0 behavior explicitly in §6.3/§6.5 and add it to the §6.7 EditMode oracle (empty broadphase -> proxy converges to physical tool, ΔP->0, no phantom force).

## S3 ['has-blocking-issues', 'has-blocking-issues']

### IMPORTANT: ProxyRelax (§6.3, L398-422) sizes the cooperative thread group and groupshared arrays with a RUNTIME counter K=candidateTriCounter ("一个含 K 线程的线程组", `groupshared float3 gs_Dvec[K], gs_len[K]`), and never specifies what threads with tid>=K do. In HLSL SM5.0 both [numthreads] and groupshared extents must be compile-time constants, so the real group must be a fixed CANDIDATE_CAPACITY with only K active lanes. The pseudocode's references to triangle_j, gs_Dvec[tid] (L410), the two GroupMemoryBarrierWithGroupSync calls (L411, L420), and the argmin reduction (L413) leave the inactive lanes unhandled — re-opening the exact divergent-barrier UB that S3-IMP2 (L398) was added to close for `break`.
FIX: In §6.3: (1) Fix the group to a compile-time `[numthreads(CANDIDATE_CAPACITY,1,1)]` and declare `groupshared gs_Dvec[CANDIDATE_CAPACITY], gs_len[CANDIDATE_CAPACITY]` (reuse the same constant already defined for the broadphase guard at L196/L473), never K. (2) State the group-uniform-masking invariant next to the S3-IMP2 break-uniformity note: EVERY thread (including tid>=K) executes the full outer loop body and both GroupMemoryBarrierWithGroupSync calls every iteration; threads with tid>=K skip the inner SDF loop and write gs_Dvec[tid]=sentinel, gs_len[tid]=+INF before barrier#1 so the reduction ignores them. (3) Thread 0's reduction at L413 scans only j in [0,K) (or relies on the +INF sentinel so scanning all lanes is also safe); if K==0 the reduction yields the sentinel and falls into the Move-Proxy (gs_done=2) branch at L415-416, so the proxy chases the physical tool and exits cleanly. (4) Add this as a third bullet in §3.8/§2 (PAPER-SILENT) alongside S3-IMP2 and S3-IMP3. (5) Add EditMode/oracle cases in §6.7 for K=0 and K=1: must not hang (all barriers group-uniform) and must hit the sentinel/Move-Proxy branch with ΔP→0 (no phantom force).

FIX: Add a persisted colliding flag and gate the damping terms with it. (1) §3.8: add `uint colliding` to hapticOutBuf (or toolStateBuf), and list it in the manifest. (2) §6.3: at the tid==0 writeback (L422), set colliding = (gs_done==1) ? 1 : 0 (i.e. 1 only on penetration-converged break; 0 when gs_done==2 not-colliding or maxOuter exhausted), and write it to the buffer alongside P_B/q_B. (4) Optionally have ScatterReactionForce skip scatter when colliding==0 (no contact ⇒ no reaction force) for consistency. (5) §6.7: add an EditMode oracle — moving tool, not colliding ⇒ F==0 AND τ==0 (no residual damping), complementing the existing IMP6 check that only verifies ΔP→0.

So the haptics->physics hand-off #4 (§6.5 L434) has an undefined source.
FIX: Add a carrier for the contact triangle id and wire it through. Concretely: (a) Extend vmsBuf to float4 + int (or add a sibling single-element contactTriBuf): when ProxyRelax tid==0 computes v_ms = argmin_j gs_len[j] at §6.3 L413, also record the winning candidate's triBuf index (the candidateTriBuf entry for thread j) and write it alongside v_ms. (b) §6.4 ScatterReactionForce reads that triBuf index, fetches triBuf[idx] = (v0,v1,v2), decodes each via the §3.4 high-bit rule to voxelId, expands to voxelCornerBuf[8], and atomicAddFixed(F) into toolReactionBuf for alive corners (gated by the contact flag / reactionForceThreshold). (c) State this carrier explicitly in §3.8 and reference it in §6.4, and either change §6.4's "接触三角" to match the chosen semantics or, to follow the paper's plural "nearby triangle faces", record the small set of candidate triangles within the contact tolerance (e.g. those with gs_len < r) and scatter into all of them. (d) Add the carrier decision to the §2 PAPER-SILENT list since the paper does not specify singular vs plural.

### minor: The q_B writeback predicate '碰撞?' (colliding?) at §6.3 L422 ('q_B = (碰撞? slerp(q_B,q_A,a_o) : q_A)') is not formally bound to the gs_done exit code, and is undefined for the maxOuter-exhaustion exit path. FIX: Define the boolean once, e.g. 'colliding := (gs_done==1) OR (loop exited by maxOuter while still penetrating)'. State it explicitly at §6.3 L422 in place of the bare '碰撞?', persist it (see problem #1's carrier), and confirm the maxOuter-exhaustion branch is treated as colliding so q_B slerps toward q_A and the damping term stays active for a still-penetrating proxy.
