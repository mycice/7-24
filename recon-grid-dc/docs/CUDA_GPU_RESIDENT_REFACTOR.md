# CUDA GPU 常驻式重构设计

## 1. 目标与边界

长期目标是建立一条统一的 CUDA GPU 常驻器官处理管线：

```text
CPU 工具输入（Haply / 键盘 / Inspector）
  -> CUDA 四面体 XPBD + 地面碰撞 + 夹爪接触/抓取
  -> CUDA Tet-to-Grid 映射
  -> 现有 CUDA 切割与 Dual Contouring
  -> Unity 直接使用 GPU 渲染缓冲区
```

运行期间，四面体位置、规则网格角点、切割状态和重建表面数组必须常驻 GPU。CPU 与 GPU 之间只传输少量控制输入、配置变更、错误信息、计数器和可选诊断数据。初始化阶段允许上传拓扑、静止位置、材料参数、嵌入映射数据和渲染缓冲区容量。

现有 Haply/CUDA 切割效果、XPBD 响应、碰撞、抓取和视觉效果是迁移验收基准。在替代路径通过对照测试前，新旧路径必须通过 Inspector 开关并存。不得在首次引入替代模块的同一阶段删除旧路径。

## 2. 目标资源归属与执行顺序

原生 `LiverCudaSim` 插件为每个器官持有一个 `CudaOrganContext`。每个 context 独立持有四面体状态、约束、接触缓冲区、Tet-to-Grid 嵌入数据、规则网格/切割状态、Dual Contouring 输出、CUDA stream、event 和容量信息。不得继续增加进程级可变 CUDA 全局状态，这是支持多器官的必要条件。

每个仿真步的执行顺序如下：

1. 异步上传小型工具/输入数据包。
2. 求解四面体 XPBD、地面碰撞、夹爪碰撞和抓取约束。
3. 在 GPU 上根据四面体位置更新规则网格角点。
4. 执行现有切割检测、拓扑更新和 Dual Contouring 内核。
5. 将重建表面发布到 Unity 持有的 GPU 渲染缓冲区。
6. 仅在请求时返回状态或计数器；禁止强制读取完整数组。

初期每个器官使用独立的 CUDA stream。只有单器官正确性得到确认后，才能增加多器官并发调度。CUDA 内核本身已经使用 GPU 并行计算，多 stream 并发属于后续优化，不能替代正确的器官资源归属设计。

## 3. 五个迁移阶段

### 阶段一：原生 Context、性能基线与对照框架

引入基于句柄的原生 API 和 `CudaOrganContext`，但暂时不改变实际仿真结果。初始化时上传一次不可变的四面体拓扑和静止数据，增加耗时、传输量和状态计数，并建立确定性的 CPU/CUDA 对照工具。当前 Unity XPBD 和 Stage 3 Bridge 继续作为实际运行路径。

验收条件：项目可以编译；当前场景行为保持不变；context 创建、销毁和场景重载无泄漏；初始化数据数量和哈希一致；记录 FPS、传输字节和帧时间基线。

### 阶段二：CUDA 四面体 XPBD

将 Stage 1 显式四面体 XPBD 状态和约束迁移到 context，包括积分、边/体积或 Neo-Hookean 约束、阻尼、重力、地面碰撞、子步和材料参数。首先让旧 Unity XPBD 与新 CUDA XPBD 运行在对照模式中，只有一个路径可以驱动显示和后续耦合。

验收条件：静止、自由落体、地面碰撞和稳定结果处于书面规定的误差容限内；无 NaN 或能量爆炸；参数变化趋势一致；CUDA 模式下不再逐帧把四面体位置从 GPU 读取到 CPU。

### 阶段三：CUDA 夹爪碰撞与抓取

使用阶段二的 CUDA 四面体缓冲区，将候选生成、工具接触、摩擦/阻尼、耦合轮次、抓取选择和抓取约束迁移到 CUDA。C# 只发送夹爪 jaw/capsule 位姿、按钮状态和参数变更。保留当前键盘和 Haply 控制组件。

验收条件：推动、挤压、闭合、夹住、提起、移动、张开和释放全部通过；穿透和形变效果与当前实现接近；器官不会飞走；接触过程不触发完整数组回读；没有接触时新增开销可以忽略。

### 阶段四：GPU Tet-to-Grid、切割融合与直接渲染

初始化时上传一次宿主四面体 ID 和重心坐标权重，运行时根据 CUDA 四面体位置计算全部规则网格角点。该输出直接连接现有 CUDA 切割和 Dual Contouring 管线。使用 CUDA 图形互操作将表面直接写入 Unity GPU 顶点、法线和辅助缓冲区，替换 `LCS_GetSurface` 与 `Mesh.SetVertices/SetNormals`。保留手动诊断回读接口，但正常帧循环禁止调用。

验收条件：器官映射位置和形变与当前 Stage 3 结果一致；垂直、水平、对角线和任意方向切割保持已验证的尺度与精度；渲染过程不再强制读取表面数组；夹爪碰撞/抓取和切割可以同时工作。

### 阶段五：多器官资源归属、旧路径清理与最终性能验收

创建多个彼此独立的 context，每个 context 持有自己的拓扑、参数、工具、CUDA stream 和渲染资源。增加确定性的生命周期和图形设备丢失处理。只有所有一致性测试通过后，才禁用并删除旧的逐帧 CPU Bridge 和回读路径，同时保留明确的调试回退模式。

验收条件：至少两个器官可以独立运行且状态不串扰；可以夹取一个器官并同时切割另一个器官；反复重载场景不泄漏 GPU 内存；Profiler 和原生计数器确认不存在逐帧大数组 CPU/GPU 传输；记录最终 FPS 和帧时间对比。

## 4. 验证规则

- 每次替换前都要记录基线：网格数量、四面体包围盒/重心、接触深度、抓取粒子数、切割计数器、表面包围盒、FPS、CPU 帧时间、GPU 帧时间和传输字节数。
- 同一时间只能有一个实际驱动路径。对照模式可以同时运行两个求解器，但不能让两者同时写入同一个器官状态。
- 每个新增原生 API 都必须检查句柄、容量和设备指针，并返回明确错误码。
- 诊断回读只能手动触发或低频采样，不得隐式成为每帧依赖。
- 不得通过修改材料、接触、切割或缩放参数来掩盖迁移差异。任何有意参数变更都需要独立测试和说明。
- DLL 使用 Release、`sm_86` 构建，只构建 `LiverCudaSim`。Unity 关闭后再部署，并报告路径、修改时间、大小、SHA256 和必要导出接口。

## 5. 完成定义

满足以下条件时，CUDA GPU 常驻式重构才算完成：正常 Play 模式下，不再有完整四面体数组、规则网格数组或重建表面数组逐帧穿过 CPU 边界；碰撞、抓取、切割、重力和渲染通过现有功能测试；多个 `CudaOrganContext` 可以彼此独立运行。少量控制输入和可选状态/诊断数据传输仍属于正常行为。
