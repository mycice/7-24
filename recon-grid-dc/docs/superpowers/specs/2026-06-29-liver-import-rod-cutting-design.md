# Liver `.msh` Import + Interactive Rod Cutting — Design Spec

**Date:** 2026-06-29
**Status:** Design draft → multi-subagent audit next
**Paper basis:** reuse the EXISTING implemented algorithms — swept-plane M-T cut detection (§2.1.3, Fig 2.8), mass-spring deformation (§2.2, Eq 9), DC reconstruction (§2.1.1) — VERBATIM. The model-import + interactive-input layers are paper-silent engineering; the mesh→grid conversion uses a mature established method (cited below).
**User decisions (2026-06-29):** keyboard control · deformable + anchored · keep the DC reconstructed-surface debug draw + a rod gizmo, defer the realistic liver material.

## Problem & goal

Replace the current synthetic sphere demo with a **real liver model** loaded from a tetrahedral `.msh`, simulated as a deformable soft body on the existing reconstructed grid, and cut in real time by an **interactive keyboard-driven rod** that replaces the auto-swept blade. **No algorithm change** to the cut/physics/DC core — this is an import + input + wiring layer. Realistic liver rendering is out of scope (the DC surface is drawn with a debug material so the cut is visible; the user has separate rendering requirements).

## Input asset (verified)

`Assets/StreamingAssets/liver3_refined_1.msh` — **gmsh ASCII format 4.1**, one volume entity, **13,412 nodes**, **58,776 tetrahedra** (element type 4), **no surface/boundary entities** (so the boundary triangulation must be derived). Node bbox ≈ `min(-11.005, -3.350, -3.294)` → `max(6.818, 6.554, 6.758)`, extent ≈ **17.82 × 9.90 × 10.05** (units unspecified by the file).

## How the existing pipeline ingests geometry (integration points — verified)

- `BackgroundGrid.Build(ILevelSetProvider ls, int3 dims, float L, float3 origin)` is the SOLE geometry entry. It samples `ls.Sample(p)` (signed: <0 inside) + `ls.Gradient(p)` (outward ~unit) at every grid corner `p = origin + coord*L`, once at preprocess, to build `cornerInside`, `cornerActive`, `voxelOccupied`, the per-voxel isect windows (`IsectEntry{globalRest, normal, cornerA, cornerB, t, insideA}`, crossing `t = fa/(fa-fb)`, `normal = ls.Gradient`), `surfaceEdges`, `gridEdges`, and the mass-spring topology. → **Importing the liver = implementing `ILevelSetProvider` from the mesh + sizing `(dims, L, origin)` to the liver bbox.** Nothing downstream changes.
- `CuttingTool{S, E, D}` is a moving segment (`S` top, `E` bottom) + thickness `D`, with `Advance(newS, newE)` rolling `Sprev/Eprev` and recomputing the swept-quad + `NCut` + `Valid` (degenerate guard when the swept area ≈ 0). → **The rod IS this tool**; driving `S`/`E` from keyboard input replaces the auto-sweep.
- `CutDetector.Dispatch(tool, rb, dims, voxelL, gridOrigin)` M-T-tests the swept quad against the **REST (undeformed) lattice** (`rest pos = gridOrigin + coord*voxelL`) — the cut targets a fixed *material* plane (immune to the gravity-vs-sweep race), and the cut point is emitted on the deformed edge. Then `SeverLinks`. Cut bits + points are **cumulative** (never reset per frame). → reused VERBATIM; the rod passes the SAME `(dims, voxelL, gridOrigin)` used by `Build`.
- `ReconGridManager` is the reference wiring: `Build → pin → ReconBuffers(g, triCapacity) → Upload → ExtForce(gravity) → MassSpringSolver(physics) → DualContouring(recon, cutting) → CuttingTool + CutDetector → dc.Build`; per frame `solver.Step → tool.Advance → cutDetector.Dispatch → solver.ComputeRotations → dc.Build → DrawProceduralIndirect`. → the new manager mirrors this, swapping the level-set source + the blade driver.

### 1. `MshLoader` — `Assets/ReconGridDC/Preprocess/MshLoader.cs`
Parse gmsh **4.1 ASCII** (the only format this asset uses; reject others with a clear error). Produce `MshMesh { Vector3[] nodes; int4[] tets; }`, then **extract the boundary surface**: a triangular face (a tet's 4 faces) is on the boundary iff it belongs to **exactly one** tet. Build a face→count map (canonical key = sorted vertex triple); emit each count-1 face **oriented outward** (the winding that puts the tet's 4th/opposite vertex on the negative side). Output `MshSurface { Vector3[] verts; int3[] tris; }`.

**Verified gmsh 4.1 ASCII layout (confirmed against `liver3_refined_1.msh`).** The block structure below is exact — a hand-rolled reader breaks if any of it is approximated. Read with `System.IO` (see §E); whitespace-tokenize each line.

- **`$MeshFormat`** — the line inside is `4.1 0 8` (version `4.1`, file-type `0` = ASCII, data-size `8`). **Reject any version that is not `4.1`** with a clear, explicit error (`"unsupported .msh version <v>; only gmsh 4.1 ASCII is supported"`). Reject file-type `1` (binary) likewise.
- **`$Entities` … `$EndEntities`** — OPTIONAL; **skip it entirely**. The bbox is computed from the parsed node coordinates (min/max over all nodes), NOT from `$Entities`. If the section is absent, do nothing.
- **`$Nodes` … `$EndNodes`**:
  - SECTION header line: `numEntityBlocks numNodes minNodeTag maxNodeTag` (asset: `1 13412 1 13412`). **Pre-size the node arrays from `numNodes`.**
  - Loop `numEntityBlocks` times. For each block:
    - BLOCK header line: `entityDim entityTag parametric numNodesInBlock` (asset: `3 1 0 13412`). **The 3rd field is `parametric` (0/1), NOT an element type.** If `parametric == 1`, reject (or handle the extra trailing parametric coordinates per node) — this asset has `parametric == 0`.
    - Then `numNodesInBlock` lines, **each a single node TAG (one integer per line)**.
    - Then `numNodesInBlock` lines, **each a coordinate triple `x y z`**.
    - **Node tags and coordinates are TWO SEPARATE consecutive lists, NOT interleaved as `tag x y z` rows.** This is the single most error-prone gmsh-4.1 fact and the #1 way a hand-rolled reader silently corrupts the mesh. `node[k]` pairs `tags[k]` with `coords[k]` POSITIONALLY (same k-th line in each of the two lists).
  - `$EndNodes`.
- **`$Elements` … `$EndElements`**:
  - SECTION header line: `numEntityBlocks numElements minElemTag maxElemTag` (asset: `1 58776 1 58776`). **Pre-size the tet array from `numElements`** (upper bound; trim if non-tet blocks exist).
  - Loop `numEntityBlocks` times. For each block:
    - BLOCK header line: `entityDim entityTag elementType numElementsInBlock` (asset: `3 1 4 58776`; **elementType 4 = 4-node tetrahedron (tet4)**).
    - Then `numElementsInBlock` lines, each `elemTag nodeTag1 nodeTag2 … nodeTagK` (a tet row = `elemTag` + **4 node TAGS**, e.g. `593 2134 2136 2137`).
    - **Ignore non-tet element-type blocks** if present (skip the block's lines without emitting tets).
  - `$EndElements`.
- **Node-tag → dense-index remap (mandatory).** While reading nodes, build a `Dictionary<int,int>` mapping each node TAG → its dense array index (0-based). **Do NOT assume `tag == index + 1`** — this asset happens to be contiguous `1..13412`, but the loader must tolerate gaps. When reading each tet, map **all 4 node tags** through the dictionary to dense indices and **assert all 4 resolve** (fail loudly on a dangling tag). The element-side tag remap is mandatory because element rows reference node TAGS, not array positions.
- Robustness: ignore non-tet element-type blocks if present (handled above); the boundary extraction and watertightness logic operate on dense indices.
- **Watertightness check** (for the level-set sign method): assert every boundary edge is shared by exactly 2 boundary faces (closed manifold) → log a warning + fall back to the winding-number sign if violated. (This edge enumeration is REUSED by `MeshLevelSet` to build its edge→incident-faces map — see §2.)

### 2. `MeshLevelSet : ILevelSetProvider` — `Assets/ReconGridDC/Preprocess/MeshLevelSet.cs`
Signed distance field from the boundary triangles (the **not-in-paper** part → mature method).
- **Acceleration:** a uniform spatial-hash grid (or a simple median-split BVH) over the boundary triangles, built once. Query the nearest triangle(s) within an expanding radius.
- **Unsigned distance:** `min` point-to-triangle distance (standard closest-point-on-triangle: project, clamp to the triangle's Voronoi regions — face/edge/vertex). **The closest-point routine MUST also REPORT which feature was closest** (FACE / EDGE / VERTEX, and the index of that feature) so the correct pseudonormal can be selected — see the three formulas below.

- **Adjacency data built ONCE in `Build` (at load), alongside the boundary extraction:**
  - a **face → outward-face-normal** list (one unit normal per boundary tri, the by-construction outward winding from §1);
  - an **EDGE map**: edge-key (sorted vertex pair) → its **2 incident boundary faces**. The watertight check in §1 already enumerates every boundary edge and counts its incident faces — **reuse that enumeration** to populate this map (no separate pass);
  - a **VERTEX map**: vertex → list of `(incident face normal, incident angle of that face AT this vertex)` over all boundary faces touching the vertex. The incident angle is the interior angle of the triangle at that vertex (`acos` of the normalized edge vectors from the vertex to its two triangle-neighbors).

- **Sign — angle-weighted pseudonormal** (Bærentzen & Aanæs 2005). The pseudonormal `n_pseudo` depends on which feature the closest-point routine reported:
  - **closest feature = FACE** → `n_pseudo` = the face normal.
  - **closest feature = EDGE** → `n_pseudo` = the (equal- or area-weighted) sum of the edge's **2 incident face normals** (from the EDGE map), then normalized.
  - **closest feature = VERTEX** → `n_pseudo` = the **INCIDENT-ANGLE-weighted sum** of the vertex's incident face normals: `n_pseudo = normalize( Σ_f angle_f · normal_f )` over faces `f` touching the vertex (from the VERTEX map). **This angle weighting is the crux of Bærentzen–Aanæs** and is REQUIRED for a correct sign when a vertex is the closest feature — which happens for many grid corners near convex/concave boundary regions (not a rare case).
  - `sign = sign(dot(p − closestPoint, n_pseudo))`. Provably correct regardless of which feature is closest, for a watertight, consistently-oriented mesh.

- **`Sample(p)`** = `sign * unsignedDistance` (unchanged).
- **`Gradient(p)`** = `sign * normalize(p − closestPoint)` — the unit outward SDF gradient. **Keep the `* sign`:** it yields the OUTWARD surface normal both inside and outside, matching `SphereLevelSet`'s convention (inside, `normalize(p − closest)` points INWARD, and the `sign` (= −1 inside) flips it back outward). This is CORRECT — do not remove the sign.
  - **Epsilon fallback (NaN guard, mandatory):** when `length(p − closestPoint) < 1e-8` — i.e. `p` lies exactly ON the surface — `normalize(p − closestPoint)` is `0/0` → NaN. **`BackgroundGrid.cs:146` calls `ls.Gradient(pos)` EXACTLY at the crossing point**, so this case WILL be hit in normal operation, not just theoretically. In that branch, return a safe unit vector instead: the closest feature's pseudonormal `n_pseudo` (already computed, and already the correct outward direction), or a constant `float3(1,0,0)` fallback as `SphereLevelSet` does. Never return a zero or NaN gradient.

- **Fallback (documented):** if the boundary fails the watertight check, sign via the **generalized winding number** (Jacobson et al. 2013, libigl `signed_distance`) — robust to holes/non-manifold defects. Pseudonormal is the default (faster, O(1) sign); winding-number is the safety net.
- **Orientation-consistency note:** the boundary faces derived from tets are consistently outward-oriented **BY CONSTRUCTION** (each count-1 face is oriented by its tet's opposite/4th vertex — §1). So the watertight check (every boundary edge in exactly 2 faces) PLUS this by-construction orientation together guarantee a valid, sign-consistent pseudonormal field; the winding-number fallback covers any violation of either property.
- **Cost:** `Build` samples φ at all corners ONCE (preprocess). The brute-force cost is `O(corners × tris)` ≈ `52k × ~10k` ≈ **5e8 closest-point tests — borderline but TOLERABLE for a one-time preprocess** (seconds, not interactive). The spatial-hash/BVH is therefore **STRONGLY RECOMMENDED** (and is the design) to bring this to ~1 s, but it is not strictly mandatory for correctness — the brute force is slow, not impossible. (See Risks R3.)

### 3. Grid fitting — `GridFit.FitToBounds(min, max, targetLongAxisVoxels, marginVoxels) → (int3 dims, float L, float3 origin)`
(a small static helper, in `MeshLevelSet.cs` or a `GridFit.cs`). `L = maxExtent / targetLongAxisVoxels`; `dims = ceil(extent / L) + 2*marginVoxels` per axis; `origin = min − marginVoxels*L`. So `origin + coord*L` (coord ∈ [0,dims]) covers the liver + a margin shell of empty voxels (needed so `cornerActive`/`voxelOccupied` have an outside ring → the DC surface closes). Default `targetLongAxisVoxels` tunable (start ≈ 48 → `L ≈ 0.37`, `dims ≈ (52, 31, 31)`, ~52k corners); `marginVoxels = 2`.

### 4. Interactive rod — `RodController` (logic in `LiverCutManager`, no separate MonoBehaviour needed)
The rod = a segment with center `C`, unit axis `a`, length `Lr`, thickness `D` (= the cut gap, reuse `bladeD`-style sub-voxel value). `S = C + (Lr/2)*a`, `E = C − (Lr/2)*a`. Each frame, read keyboard → update `C` and `a` → `tool.Advance(S, E)`.
- **Keyboard map (tunable):** translate `C` — `W/S` = +/−Z, `A/D` = −/+X, `Q/E` = +/−Y (world axes; speed `moveSpeed` units/s × `dt`). Rotate `a` — arrow keys pitch/yaw (or `R/F`, `T/G`; speed `rotSpeed` deg/s × `dt`). Optional `[`/`]` adjust `Lr`. (Final keys can be tuned in the Inspector / adjusted on review.)
- **Cutting semantics:** when the rod moves, the swept quad `(Sprev,Eprev,E,S)` is non-degenerate (`Valid=true`) → `DetectCut` severs the rest-lattice edges the quad crosses, exactly as the auto-sweep does. Holding still ⇒ `Valid=false` ⇒ no cut that frame (correct: not cutting). Per-frame motion should stay `< L` to avoid skipping a rest-edge layer (mirror the demo's `bladeSpeed*dt < L` coverage warning).
- **Sub-stepping the rod delta (fast-sweep / teleport guard) — REQUIRED.** `CuttingTool.Valid` only rejects ZERO motion (swept area `< 1e-8`); it has **NO upper bound**. A fast keyboard sweep, or a discontinuous jump (large rotation, big length change, or big translation in one frame), makes ONE swept quad span the entire jump → `DetectCut` severs **every** rest edge crossing that giant quad in a single frame (an unintended cut swath) AND **skips intermediate rest-edge layers** (no clean progressive cut). Mitigation: each frame, take the rod's delta (prev pose → new pose) and **SUB-STEP it** — subdivide the move into `N` sub-steps such that **each sub-step's endpoint travel `< L`** (i.e. `N = ceil(maxEndpointDisplacement / L)`, mirroring the demo's `bladeSpeed*dt < L` coverage rule), and call `tool.Advance(...)` + `cutDetector.Dispatch(...)` **once per sub-step**. Cuts are cumulative, so the sub-steps compose into exactly the intended sweep. This bound also keeps each individual swept quad small (well-conditioned M-T tests). (See Risks R7.)

### 5. `LiverCutManager` — `Assets/ReconGridDC/Demo/LiverCutManager.cs`
A MonoBehaviour mirroring `ReconGridManager`, with these swaps:
- **GPU asset acquisition (mirror `ReconGridManager`):** declare the SAME PUBLIC serialized fields and wire them via the Inspector — `public ComputeShader recon; public ComputeShader physics; public ComputeShader cutting; public Shader surfaceShader;`. Compute shaders **cannot** be obtained via `Shader.Find` (that resolves only graphics `Shader` assets, not `ComputeShader`s) — they require an Inspector drag-drop OR an editor-only `AssetDatabase.LoadAssetAtPath` in a setup script. The surface shader CAN be `Shader.Find("ReconGridDC/ReconSurface")` (as `DemoSceneSetup` does). **Recommendation: add a `LiverSceneSetup` editor/setup script mirroring `DemoSceneSetup`** — it `Shader.Find`s `"ReconGridDC/ReconSurface"` for `surfaceShader` and `AssetDatabase.LoadAssetAtPath`s the three `.compute` assets to wire `recon`/`physics`/`cutting` (rather than extending `DemoSceneSetup`, which targets `ReconGridManager`). The **debug material** is literally `new Material(surfaceShader)` (the `ReconGridDC/ReconSurface` shader) — no special liver material.
- **Start():** load `.msh` via `MshLoader` (path under `Application.streamingAssetsPath`) → `MeshLevelSet` → `GridFit.FitToBounds(bbox)` → `BackgroundGrid.Build(meshLS, dims, L, origin)` → **anchor** (pin a region, below) → `ReconBuffers(g, triCapacity)` (`triCapacity = 6*surfaceEdges + 1024 + 2*gridEdges`, same formula) → `Upload` → `ExtForce = (0, gravity*mass, 0)` → `MassSpringSolver(physics)` → `DualContouring(recon, cutting)` → `CuttingTool(S0, E0, rodD)` + `CutDetector(cutting)` → initial `dc.Build` → debug material (`new Material(surfaceShader)`) + render bounds (AABB of `origin .. origin+dims*L`, padded for sag).
  - **Empty/all-outside grid guard (REQUIRED):** after `Build`, assert `voxelOccupied` contains BOTH 0s and 1s (the liver is partly inside AND there is an outside ring). A mis-sized `origin`/`L` (liver entirely outside, or entirely filling, the grid) yields `surfaceEdges.Length == 0` → `triCapacity` tiny → `DrawProceduralIndirect` draws nothing (a silent blank). Fail loudly in `Start()` with a clear message, and cover it with a test (see Testing #8).
  - **Anchor guard (REQUIRED):** after pinning, assert **≥1 corner is pinned** (else the body free-falls with no error). Fail loudly if zero corners fall in the band, and cover it with a test (see Testing #9).
- **Anchor (deformable + pinned, per user):** pin tissue corners (`cornerActive==1`) within a band at one end of the bbox (default: the `+X` cap, `x ≥ maxX − anchorBand`), so the liver deforms/sags under gravity but does not free-fall. **The anchor axis/end AND the band thickness must be tunable** (Inspector fields), since the right band depends on `L` and the liver orientation; the guard above asserts the chosen band actually pins ≥1 corner.
- **Update():** `solver.Step` → read keyboard + compute the new rod pose → **sub-step the rod delta** (§4): for each of the `N` sub-steps (`N = ceil(maxEndpointDisplacement / L)`), `tool.Advance(S_i, E_i)` then `cutDetector.Dispatch(tool, rb, dims, L, origin)` (SAME origin as Build) → `solver.ComputeRotations` → `dc.Build` → `DrawProceduralIndirect` (debug material) + draw the rod as a **persistent `LineRenderer` from `S` to `E`** (single chosen mechanism — not a Debug.DrawLine/OnDrawGizmos alternative), optionally with a faint `D`-offset wall.
- **Physics scaling (flagged):** the liver (~18 u) is ~3× the sphere demo (~6 u). The existing `ks/gravity/dt/mass/cs/kb/cb` are tuned for the small case. Expose them all in the Inspector with conservative starting defaults and DOCUMENT the stability risk; do not silently assume the sphere tuning transfers. The dominant stability knobs are `ks` and the integrator substep size — see Risks R1.

## Data flow
`.msh` → `MshLoader` (verts + boundary tris) → `MeshLevelSet` (pseudonormal SDF) → `BackgroundGrid.Build(meshLS, dims, L, origin)` → `ReconBuffers.Upload` → **[per frame]** keyboard → rod `S/E` → `CuttingTool.Advance` → `solver.Step` (deform) → `CutDetector.Dispatch` (rest-frame M-T cut + `SeverLinks`) → `solver.ComputeRotations` → `dc.Build` (DC surface + cut walls) → `DrawProceduralIndirect` + rod gizmo.

## Testing
CPU tests (`[Test]`, no GPU) for the new pure logic; integration is a play-mode/manual check. All CPU tests live in the existing `ReconGridDC.Tests` asmdef (§Architecture bookkeeping) — do NOT add a new test asmdef.
1. **MshLoader parse:** load the liver `.msh` → assert 13,412 nodes, 58,776 tets, node bbox matches the verified extent. **Tolerance ±1e-2** (NOT ±1e-3): the file coords are ~16 significant digits parsed into `float32`, so float-precision rounding can exceed 1e-3 on the larger coordinates; use ±1e-2 (or compare with `float`-precision epsilon scaled to magnitude).
2. **Boundary extraction:** the extracted surface is a **closed manifold** (every boundary edge shared by exactly 2 boundary tris) and **outward-oriented** validated by an **INDEPENDENT signed-volume / divergence test** (sum over boundary tris of the signed tetrahedron volume to the origin, `Σ (1/6)·dot(v0, cross(v1, v2))`; the magnitude equals the enclosed volume and a **consistent positive sign ⇒ consistent outward winding**). **Do NOT validate orientation by "the centroid samples inside per the sign method"** — that is circular (it uses the very pseudonormal sign method under test). Triangle count > 0 and ≪ 4*tetCount.
3. **MeshLevelSet sign:** a point at the bbox center samples `< 0` (inside); a point far outside samples `> 0`; on a cube-mesh built inline, `MeshLevelSet.Sample` matches `BoxLevelSet.Sample` within the discretization tolerance, and `Gradient` is ~unit + agrees with the analytic box normal away from edges.
4. **MeshLevelSet distance:** unsigned distance at sampled probes matches a brute-force min-over-triangles reference (±1e-4).
5. **GridFit:** `origin + dims*L` covers `[min−margin, max+margin]` on every axis; `dims ≥ 1`.
6. **Rod input math:** a keyboard sequence maps to the expected `S/E` (center/axis/length → endpoints); a stationary frame yields `Valid==false`, a moving frame `Valid==true`. **Sub-stepping:** a delta with `maxEndpointDisplacement > L` produces `N = ceil(maxEndpointDisplacement / L)` sub-steps each with travel `< L`.
7. **Integration (manual, user in Unity):** the liver builds, sags under gravity anchored at one end, the keyboard rod sweeps through it and opens a visible cut with no NaN; zero-motion = no spurious cut; a deliberate fast sweep still cuts progressively (no swath, no skipped layers — validates sub-stepping).
8. **Empty/all-outside grid guard (CPU):** after `Build` on a correctly-fit grid, `voxelOccupied` contains BOTH 0s and 1s (and `surfaceEdges.Length > 0`); a deliberately mis-sized `origin`/`L` (liver fully outside) trips the guard (`surfaceEdges.Length == 0`). Mirrors the `Start()` assert.
9. **Anchor guard (CPU):** the anchor band pins **≥1 corner** with `cornerActive==1` for the default band/end; a zero-thickness or wrong-end band pins 0 and trips the guard. The band thickness and end/axis are tunable inputs to the test.

Each task ends with a **multi-subagent code review** verifying the new code matches (a) this spec and (b) the reused paper algorithms' contracts (it must NOT alter them) — per the user's standing requirement.

## Decisions
- **Mesh→SDF = angle-weighted pseudonormal** (Bærentzen & Aanæs 2005) + spatial-hash/BVH acceleration; **winding-number** (Jacobson 2013 / libigl) fallback for defective boundaries. Chosen over binary point-in-tet voxelization (which gives a blocky, gradient-less field — DC needs a smooth signed field + outward normals for crossing `t` and feature-point QEF).
- **Keyboard control** (no camera/raycast dependency) — per user.
- **Deformable + anchored**, pin a bbox-end band — per user.
- **Keep the DC surface debug draw + rod gizmo**; defer the realistic liver material — per user.
- **Liver in native coordinates**; grid sized to bbox + margin (negative origin is fine; passed identically to `Build` and `CutDetector`).
- **Rod = `CuttingTool` segment**; cut detection in **rest/material space** (verbatim reuse of the existing rest-frame `DetectCut`).
- **GPU asset wiring** = mirror `ReconGridManager`'s public serialized fields (`ComputeShader recon/physics/cutting`, `Shader surfaceShader`), wired in the Inspector; add a **`LiverSceneSetup`** editor/setup script (mirroring `DemoSceneSetup`) that `Shader.Find`s `"ReconGridDC/ReconSurface"` and `AssetDatabase.LoadAssetAtPath`s the three `.compute` assets (compute shaders cannot be `Shader.Find`'d). Debug material = `new Material(surfaceShader)` (ReconSurface) — no liver-specific material (deferred per user). (See §5.)
- **Rod gizmo** = a single mechanism — a **persistent `LineRenderer`** from `S` to `E` (not a Debug.DrawLine / OnDrawGizmos menu). (See §5.)

## Risks
- **R1 (top) — physics scale/stability:** the liver is ~3× the demo's size; reusing the sphere's tuning may be unstable or sluggish. **Primary mitigation (corrected):** the explicit-RK integrator's stability limit is governed by the **solver substep size (`hMax` / substep count) vs the spring stiffness `ks`** — these are the real knobs (a stiffer `ks` or larger `hMax` blows up first). **Gravity and the anchor are SECONDARY** (they set the load/boundary, not the integration stability threshold). So: tune `ks` down and/or the adaptive integrator's `hMax`/substep-count up first; treat reduced gravity / stronger anchor as secondary aids. All params Inspector-tunable, conservative defaults, documented tuning note. NOT an algorithm change.
- **R2 — rest-frame cut vs deforming tissue (strengthened):** `DetectCut` cuts the REST material plane. Its own validity premise is explicit in `Cutting.compute:68` — *"the demo is pure translation; X/Z ≡ 0 by symmetry"* — and that premise is **BROKEN** by an arbitrarily keyboard-rotated/translated rod driven into anchored, sagging, non-symmetric tissue. So this is **worse than "mild drift"**: with significant sag PLUS arbitrary rod motion, the cut targets rest material that has moved away from where the user *sees* the tissue and rod, so the visible cut can land in the wrong place (memory `dc-incomplete-cut-detection-race`). **Honest mitigation:** keep deformation MILD for the demo (modest gravity, firm anchor) so rest ≈ deformed; document that a **deformed-frame detector is the real fix** (overlapping the deferred MT/ablation work) and is a **stronger prerequisite for large-deformation cutting than the spec previously admitted** — not a mere "future enhancement."
- **R3 — SDF preprocess cost:** `O(corners × triangles)` ≈ 5e8 closest-point tests — **borderline but tolerable** for a one-time preprocess (seconds). The spatial-hash/BVH is **strongly recommended** (brings it to ~1 s) but not strictly mandatory for correctness; validate build time and add acceleration if the brute force is too slow in practice. (Softened from "mandatory / impossible".)
- **R4 — boundary defects:** a non-watertight/non-manifold tet boundary flips the pseudonormal sign → the watertight check + winding-number fallback. (By-construction outward orientation + the watertight check together guarantee the field when both hold — §2.)
- **R5 — grid resolution vs liver features:** too coarse `L` loses thin liver parts / blockies the surface; `targetLongAxisVoxels` tunable, with the compute-cost tradeoff documented.
- **R6 — `triCapacity`:** the liver has more surface edges than the sphere; reuse the `6*surfaceEdges + 1024 + 2*gridEdges` formula (auto-scales) and verify no overflow.
- **R7 — interactive fast-sweep / teleport:** a fast keyboard sweep or a discontinuous one-frame jump (large rotation / length change / big translation) makes a SINGLE swept quad span the whole move → `DetectCut` severs every rest edge crossing that giant quad in one frame (unintended cut swath) and skips intermediate rest-edge layers. `CuttingTool.Valid` has no upper motion bound (only rejects zero motion), so it does not catch this. **Mitigation: sub-step the rod delta** so each sub-step's endpoint travel `< L` (§4 / §5 Update), calling `tool.Advance` + `cutDetector.Dispatch` per sub-step; cumulative cuts compose into the intended sweep and each swept quad stays small.
- **Minor robustness — initial rod pose / cut-plane offset:** carry over the demo's `+L*0.5` cut-plane offset rationale — offsetting the cut plane by half a voxel **avoids double cut-point emission when the cut plane sits exactly on a corner layer**. Apply the same half-voxel offset consideration to the rod's initial pose so the first sweep does not start exactly coincident with a rest-corner layer.

## Out of scope
- Realistic liver rendering / material / shading (the user's separate requirements).
- Mouse control (keyboard chosen).
- Ablation / volume-loss cutting (shelved — see memory `ablation-2d3-shelved`).
- Haptics, collision response, multi-tool.
- Re-tuning the physics constants to physical liver values (only expose + document; tuning is a follow-up).
